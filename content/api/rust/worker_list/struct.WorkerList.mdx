<div className="docblock">
<p>A list of worker URLs to use for multi-head operations.</p>
<p>The addresses belong to the <strong>connection</strong>, not to this list. A <a href="/content/api/rust/gpudb/struct.Kinetica" title="struct gpudb_api::gpudb::Kinetica"><code>Kinetica</code></a> instance discovers each cluster’s rank addresses, applies the connection’s hostname regex to them, and keeps the result per cluster; this struct is a view onto that, held by a bulk inserter or record retriever.</p>
<p>It does not resolve or filter addresses of its own. A filter has no coherent meaning here, because it cannot survive a failover: one tuned for a cluster’s addressing may match nothing on the next, and multi-head objects fail over with the connection. Set the regex on the connection instead — see <code>KineticaOptions::set\_hostname\_regex</code> — where it is applied to every cluster as that cluster is discovered.</p>
<p>The one choice that <span className="em">is</span> meaningful per object is declining multi-head altogether; see <a href="/content/api/rust/worker_list/struct.WorkerList#method.empty" title="associated function gpudb_api::worker_list::WorkerList::empty"><code>WorkerList::empty</code></a>. That names an intent rather than an address, and an intent transfers across clusters where a list of addresses does not.</p>
<p>Note entry <code>i</code> of this list is rank <code>i + 1</code>; the head rank is not a member, and a rank removed from the cluster keeps its slot as <code>None</code>. The worker indices in the shard routing table are rank numbers, so compacting the list would silently misroute every rank above the hole.</p>
<h2 id="example">Example</h2>
<div>

```rust
use gpudb_api::{Kinetica, KineticaOptions, WorkerList};
use std::sync::Arc;

let options = KineticaOptions::new();
let kinetica = Arc::new(
    Kinetica::new(vec!["http://localhost:9191".to_string()], options).await?
);

// Use the addresses the connection discovered for its current cluster
let worker_list = WorkerList::from_cluster(&kinetica);

// Or decline multi-head for one inserter/retriever, keeping fail-over
let head_node_only = WorkerList::empty();
```

<div className="docblock">
<p>Creates an empty <a href="/content/api/rust/worker_list/struct.WorkerList" title="struct gpudb_api::worker_list::WorkerList"><code>WorkerList</code></a>, which declines multi-head operations for the bulk inserter or record retriever it is given to.</p>
<p>That object will route through the head node for its lifetime. The choice is authoritative: it is not undone when the worker list is rebuilt after a failover or a shard rebalance.</p>
<p>This is the way to decline multi-head for a single object while keeping the connection’s fail-over. Disabling auto-discovery is not equivalent — it also stops the client discovering the other clusters in an HA ring, so it costs fail-over as well.</p>
<p>Nothing inside this crate may use this constructor: it is a caller’s way of expressing an intent, and an internal use would silently pin its own list to head-node-only. Internal code wanting a list with no addresses builds one through <a href="/content/api/rust/worker_list/struct.WorkerList#method.with_urls" title="associated function gpudb_api::worker_list::WorkerList::with_urls"><code>WorkerList::with\_urls</code></a> instead.</p>

<div className="docblock">
<p>Creates a <a href="/content/api/rust/worker_list/struct.WorkerList" title="struct gpudb_api::worker_list::WorkerList"><code>WorkerList</code></a> from the worker rank addresses the given connection has already discovered for the cluster it is currently on.</p>
<p>This reads the connection’s addresses; it does not query the server or re-resolve them. They were filtered through the connection’s hostname regex when that cluster was discovered, so they already reflect it.</p>
<p>If the connection has no worker addresses for the current cluster — multi-head is off at the server, or the cluster advertises none this client can use — the list is empty and the object using it operates through the head node.</p>

<li><code>db</code> - The Kinetica instance whose addresses to use</li>

<p>Converts the worker list to a vector of URL strings.</p>
<p>This method filters out <code>None</code> entries (removed ranks) and returns only the valid URL strings.</p>
<h5 id="never-use-this-for-shard-routing">Never use this for shard routing</h5>
<p>The result is <strong>compacted</strong>, so its indices are no longer rank numbers. Routing a sharded record through these indices sends every rank above a removed one to the wrong host. Use <a href="/content/api/rust/worker_list/struct.WorkerList#method.urls" title="method gpudb_api::worker_list::WorkerList::urls"><code>Self::urls</code></a> and index by slot, or let the bulk inserter build its rank mapping from the slot positions. This is only safe where any live worker will do — round-robin distribution, health checks, and the like.</p>
<h5 id="returns-2">Returns</h5>
<p>A vector of URL strings for all valid (non-removed) workers.</p>
</div>
